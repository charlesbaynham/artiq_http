## Plan: Strict NDScan Validation + MCP Scan Builder

Add server-side submission validation that rejects malformed ndscan payloads before ARTIQ RPC, and introduce a new high-level scan-submission path (HTTP + MCP) that supports both 1D and multi-axis scans without requiring clients to handcraft full ndscan_params. Keep existing raw submission endpoints/tools for backward compatibility.

**Steps**
1. Phase 1: Baseline and contract definition. Confirm and document the accepted high-level scan request schema (axes + fixed parameter overrides + repeats + scheduling fields) and error contract (HTTP 422 for malformed/invalid request semantics, HTTP 404 for unknown experiment).
2. Phase 1: Reuse current experiment discovery path to obtain arginfo for the selected experiment (from the existing explist source) and parse ndscan schemata into a validated in-memory representation used by both validation and builder logic.
3. Phase 2: Implement strict HTTP pre-submit validation for existing submission endpoints. Validate all ndscan-specific arguments before calling RPC: ndscan_params JSON parseability, required structure keys, valid scan axis type enum, known parameter references, no overlap between scanned and fixed parameters, numeric range consistency per axis, and basic shape sanity for overrides. Return deterministic 422 messages. depends on 1-2.
4. Phase 2: Add a new backend helper that builds canonical ndscan_params from high-level scan input (axes + fixed parameters + repeats) using the parsed schema metadata so callers do not pass full ndscan_params manually. depends on 2.
5. Phase 3: Add a dedicated HTTP endpoint for high-level scan submissions that builds ndscan_params server-side and submits through the existing scheduling path. Keep /api/schedule and /api/schedule/submit-and-wait behavior backward-compatible for existing clients while enforcing new validation. depends on 3-4.
6. Phase 3: Extend MCP with new high-level tools for v1 scan submission supporting both single-axis and multi-axis scans. Tools should call the new HTTP endpoint and provide explicit, strict parameter docs (especially valid scan types and expected units). Keep existing submit_experiment/submit_and_wait tools unchanged for compatibility. depends on 5.
7. Phase 4: Add/update tests for model/endpoint/MCP behavior and failure paths (invalid JSON, hallucinated scan type, unknown axis parameter, invalid ranges, duplicate parameter across fixed+scanned, successful 1D, successful multi-axis). depends on 3,5,6.
8. Phase 4: Documentation updates for API + MCP usage with concrete scan examples and troubleshooting notes emphasizing that users provide axes/fixed params only, not raw ndscan_params. parallel with 7 after API shape is stable.
9. Phase 5: Versioning and release hygiene. Increment patch/minor version consistently in both runtime and package metadata files according to semver policy after final scope is confirmed.
10. Phase 5: Full verification on unit tests and local ARTIQ stack checks; do not merge until all green. depends on 7-9.

**Decisions**
- Strict-by-default validation at HTTP API level is in scope.
- v1 MCP ergonomics must support both 1D and multi-axis scan submission.
- Architecture choice is backend HTTP scan-builder + MCP wrapper, not MCP-only construction.
- Existing raw submission interfaces remain supported (no breaking removal in this scope).

**Further Considerations**
1. Error schema standardization: choose whether all validation errors return a single message string or structured details list; recommend structured details for easier MCP surfacing.
2. Parameter naming UX: decide whether MCP accepts human-short names, FQNs, or both; recommend both with explicit conflict resolution toward exact FQN.
3. Unit handling policy: decide whether API enforces SI only or supports declared unit scaling; recommend SI-only in v1 with explicit docs unless current frontend contract requires mixed units.
